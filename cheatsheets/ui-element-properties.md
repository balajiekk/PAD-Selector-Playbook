# UI Element Properties Cheatsheet

When a PAD UI element is unreliable, inspect its properties before rewriting the automation.

## What to inspect

| Area | Question |
|---|---|
| Name/text | Is it meaningful and stable? |
| Control type | Is the control type consistent? |
| Parent/container | Can the target be scoped more reliably? |
| ID | Is it generated or stable? |
| Class | Is it application-defined or generated? |
| Index | Does it remain deterministic? |
| Visibility/state | Is the target available at interaction time? |

## Stability rule

A property that looks unique today is not necessarily stable tomorrow.

Ask:

1. Does it change between application launches?
2. Does it change between records/rows?
3. Does it change between environments?
4. Is it generated by the framework?
5. Is another property more meaningful?

## Selector improvement sequence

```text
Inspect properties
      ↓
Remove unnecessary volatile properties
      ↓
Scope under stable parent
      ↓
Use exact stable values
      ↓
Add targeted dynamic matching only if required
      ↓
Validate across representative states
```

## Anti-patterns

- Selecting an element only because its generated ID happens to work.
- Keeping every captured property without understanding its purpose.
- Using regex as the first response to every selector failure.
- Depending on screen coordinates when a stable UI element is exposed.
